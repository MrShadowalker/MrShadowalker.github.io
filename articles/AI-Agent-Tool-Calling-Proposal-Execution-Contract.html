Tool Calling 第一课：模型提议如何变成受控工具调用

2026-11-26
AI工程
字数统计: 3.3k   |   阅读时长≈ 12 分钟

进入第二个月，我们要把第一个月的 ModelClient 接到受控工具上。最容易写错的地方是把模型返回的“我要调用某个函数”当成函数已经执行。对于自定义工具，模型只产生候选调用；应用收集参数、校验、授权、执行，并将结果用原调用 ID 交还模型。这个往返才是 Tool Calling 的最小闭环。

本文只做一个只读工具 lookup_policy_v1，聚焦协议和执行边界。已有的工具安全总览覆盖权限、审批与审计原则；今天把这些原则落成可实现的调用记录和失败路径。第 30 天的模型网关项目仍需独立实现与验收，本文不把工具示例说成它已交付。

一、工具调用至少有五个不同的事实

对象 谁产生 能证明什么 不能证明什么
ToolSpec 应用 当前允许模型看见的名称、描述和参数形状 用户有权执行
ToolProposal 模型 模型建议了什么参数 参数真实、合规、完整
PolicyDecision 服务端 当时身份、资源和任务状态是否允许 下游已执行成功
ToolInvocation 执行器 实际向哪个工具发出请求及本地执行 ID 结果已被模型正确理解
ToolResult 工具/执行器 执行回执或明确错误 最终答案一定正确

OpenAI 自定义函数调用的流程是：暴露工具，模型产生 function_call，应用执行后发送同一 call_id 的 function_call_output，再让模型继续；一次模型响应可能含多个调用。Anthropic 的对应结构是带 id、name、input 的 tool_use 内容块，后续 tool_result 用 tool_use_id 配对，失败可设 is_error: true。**call_id / tool_use_id 是供应商会话内的配对 ID，本地审计和幂等另用 execution_id。**OpenAI Function Calling、Anthropic Tool Calls（检索日期：2026-11-26）

三、执行器必须在完整参数后才跨越边界

流式模型可能逐段输出工具参数。OpenAI 有参数增量与完成事件；Claude 的工具输入也可能以 JSON 片段到达。收到 {"document_id":"policy- 时，不能抢先发出查询。只有整个调用完成，才能解析、校验并分配执行 ID。OpenAI Function Calling、Anthropic Streaming messages（检索日期：2026-11-26）

一次模型响应若有多个工具提议，要为每个调用分别保留 ID、结果和错误；只读且互不依赖的调用可以有界并行，不能把“模型同时提出”解释为“任何写操作都可同时执行”。未知工具名、参数不完整、Schema 不符或权限拒绝时，执行次数应为 0；返回给模型的是受控错误码，不泄露另一个租户的文档是否存在。

工具结果同样是不可信输入。它可以包含用户写的政策文本，甚至“忽略之前的规则”之类恶意句子；回填模型时作为工具数据，不升级为系统指令。最终回答中的引用 ID 还要由服务端核对，不能因为模型看过工具结果就跳过授权。OWASP LLM03:2026 Excessive Agency（检索日期：2026-11-26）

执行器将这份结果按供应商协议回传：OpenAI 使用原 call_id 的 function_call_output；Anthropic 使用原 tool_use_id 的 tool_result。内部 execution_id 可以用于审计，但不替代供应商的关联 ID。失败时使用可解释的 INVALID_ARGUMENTS、NOT_FOUND_OR_FORBIDDEN、TOOL_TIMEOUT 等错误分类，保留真实执行记录，再决定是否允许模型修正参数。模型若反复用同样参数触发同样错误，运行时应按次数和截止时间停止循环，而不是无限“自我修复”。OpenAI Function Calling、Anthropic Handle Tool Calls（检索日期：2026-11-26）

Day 57–60 再把本地工具注册表和 MCP 接起来。MCP 的 tools/list、tools/call、inputSchema、可选 outputSchema 与错误标记提供跨进程工具协议，但输入校验、访问控制、超时和审计仍由宿主与工具服务负责；不要因为换了协议就省掉今天的执行器。MCP Tools 规范（2026-07-28）（检索日期：2026-11-26）

五、今天的最小实践

在独立练习工程中实现 lookup_policy_v1 的 FakeTool 与供应商无关的执行器；可以先只用固定模型输出夹具，不调用付费模型。保存以下五条自动断言及执行日志：

Case 输入 必须成立
正常读取 A 查询 A 的 policy-a-v4 执行一次，结果带版本；最终引用仍校验 A 的权限
越权 ID A 查询 B 的文档 业务工具执行 0 次或在服务端授权处拒绝；无 B 正文泄漏
半截参数 JSON 参数流未结束 执行次数为 0；任务等待完整调用或进入错误分支
未知工具 模型提出 execute_sql 注册表拒绝；不把工具名当命令解释
重复错误 模型连续三次提相同非法 ID 按配置的步数/时间上限结束，不无限调用

每条记录保存 task_id、provider_call_id、execution_id、工具版本、决策原因和最终状态；敏感原文只保存在受控存储。第 32 天进一步讲 Schema 版本和工具发现，第 35 天做第五周复盘；Day 30 的网关 P0 实现仍需独立补齐。

六、今日面试题（检索日期：2026-11-26）

以下题面来自公开来源。公司、岗位和场次如果依赖发帖者自述，均未获企业官方核验；参考答案与追问是本文的工程归纳。

1. Function Calling 的完整流程是什么？在项目里怎么用？

  • 方向 / 难度：工具协议、Agent 集成 / 中高。
  • 参考答案：应用先暴露当前任务允许的工具定义；模型产出带调用 ID、工具名和参数的候选调用。应用等参数完整后按白名单和 Schema 校验，再用受信身份做资源授权，记录并执行，最后用同一供应商调用 ID 回传结果，让模型继续生成。任务最终状态以执行器和业务校验为准，不能以模型提出调用作为成功。
  • 追问：参数里的设备 ID 格式合法，但设备属于另一个租户，能执行吗？不能。Schema 只能证明形状，资源归属由服务端再次校验。
  • 来源：牛客“阿里巴巴 AI Agent 应用开发一面”用户自述，页面显示 11-07；公司与场次未获官方核验。

2. 模型返回符合 Schema 的对象，与发出一次工具调用有什么区别？两者都算成功吗？

  • 方向 / 难度：结构化输出、工具执行边界 / 中高。
  • 参考答案：符合 Schema 的对象是模型生成的数据，可作为分类或草稿，但仍要验业务语义；工具调用是对某个动作的提议，必须经过执行器校验、授权和真实工具回执。两者都不自动等于任务成功；最终状态还要看工具结果、后续模型回答和业务断言。
  • 追问：模型生成 {"status":"paid"} 且 Schema 正确，能把订单改成已支付吗？不能；支付状态来自受控业务系统的可信回执，模型文本不能提交状态。
  • 来源：牛客“vivo Agent 开发工程师一面题解”用户发布内容，页面显示 11-20；题解不是可证明的逐字面试实录，公司与场次未获官方核验。

3. search_events 和 find_free_time 经常选错，怎样改、怎样验证？

  • 方向 / 难度：工具选择、离线评测 / 中高。
  • 参考答案：把两个工具的适用目标、禁用条件、参数和返回值写成互斥且可检验的描述；提供相近问题的成对反例，如“查我明天的会议”与“找明天空档”。固定模型和工具版本后评测首步工具选择率与最终任务完成率，并检查误选的代价，不能只凭一次 Demo 判断描述改善。
  • 追问：首步选择准确率提高，但最终日程草稿错误更多，怎么办？沿 Trace 查参数提取、工具结果解释和最终草稿校验，分别加样本；整体任务成功率是发布门槛。
  • 来源：牛客“vivo Agent 开发工程师一面题解”用户发布内容，页面显示 11-20；题解与公司归属未获官方核验。

4. 普通 Tool Calling 和接口也能校验参数，领域对象约束还解决什么？

  • 方向 / 难度：工具契约、业务不变量 / 难。
  • 参考答案：Schema 验字段和局部类型；接口校验可以验证即时规则。跨对象关系、版本适用性和合法状态迁移需要领域模型或明确的业务规则表达，例如“只有当前审批版本可以提交”。不论是否采用本体化建模，工具端都必须用最新业务事实和受信身份做授权，模型输出的合格参数不能绕过执行前检查。
  • 追问：模型参数合法，但订单状态在模型思考期间已改变，还能执行写工具吗？不能按旧快照盲写；执行前重读状态并做版本条件更新，冲突时要求重新确认。
  • 来源：牛客“淘天 AI Agent / 大模型应用研发一面”用户自述，页面显示 11-12；公司与场次未获官方核验。
