AI 全栈前端怎样接任务：TypeScript 状态机、SSE 去重与权限边界

2026-11-15

字数统计: 2.2k   |   阅读时长≈ 8 分钟

补刊说明：本文补齐原定第 20 天学习内容；资料与题目于 2026-11-21 检索核验。

第 19 天已经让后端输出有序事件。前端不能只写一个“正在生成”的布尔值：提交请求可能超时但任务已创建，SSE 可能断开后重复投递，用户也可能在权限被撤销时还停留在旧页面。

今天把这些情况写成一个可检查的 TypeScript 状态机。熟悉 Java 后端的读者，可以把它看成前端版的任务状态 DTO 与合法迁移表。

一、页面只保存必要状态

界面分为 idle、submitting、running、resyncing、succeeded、failed、forbidden。其中 running 保存 taskId、最后确认的事件序号与尚未完成的展示文本；成功后显示后端确认的最终答案与引用。

kind 是判别字段；TypeScript 在分支里能收窄可访问字段。它能防止“已成功但还显示错误提示”之类的非法组合，但运行时来自网络的 JSON 仍要校验，静态类型不能替代解析和授权。TypeScript Handbook：Discriminated unions、React：Choosing the State Structure（检索日期：2026-11-21）

不要在组件里另存一份可从 TaskView 算出的 isLoading、canCancel 或“当前答案”。否则两个状态更新的先后差异会制造不可能的界面。把状态放在拥有该任务卡片的组件或一个明确的共享 store 中，页面切换时用任务 ID 恢复。

二、提交超时不能当成“没创建”

提交请求使用客户端生成的稳定 Idempotency-Key。按钮防抖只减少重复点击，无法处理请求已经到达服务端、响应却丢失的情况。

若 fetch 超时或用户主动中断，用同一键和同一请求体重发 POST /v1/tasks；服务端返回原任务而不重复创建。服务端应对“同键不同载荷”返回冲突。浏览器的 AbortController 只取消本地请求等待，不能证明服务器回滚了创建任务的数据库事务。MDN AbortSignal（检索日期：2026-11-21）

三、SSE 增量只在序号连续时合并

页面首次进入或刷新时，先读取 GET /v1/tasks/{id} 快照：last_seq、任务状态、当前可展示文本与引用。之后订阅 /events?after=last_seq。重连可能重放，所以按 taskId 和 seq 去重；若发现序号跳跃，停止拼接，重新读快照。

浏览器原生 EventSource 的构造参数只有 URL 和 withCredentials 选项；若使用同源 HttpOnly 会话 Cookie，可按既有认证方式打开流。它不提供自定义 Authorization 请求头参数；Bearer Token 场景需采用受控 fetch 流解析与手动重连，或由后端签发短期、限任务的流凭证，并评估 URL、日志泄露风险。服务端每次连接都要重新鉴权。WHATWG EventSource 接口（检索日期：2026-11-21）

组件卸载时调用 EventSource.close() 释放连接；error 事件后先查询任务快照，区分暂时断网、任务终态和 403。权限失效时清除当前任务的草稿与引用，不能继续展示缓存的敏感结果。浏览器离开页面不触发任务取消；显式取消按钮才调用后端取消 API。

四、流式渲染要保住可读性

模型按 Token 送出的 Markdown 可能半个代码围栏还没闭合。展示草稿时可以按短时间窗口合并增量，先以纯文本或可处理未闭合块的渲染器显示，成功后再渲染经过净化的最终 Markdown。不要用原始模型文本直接填 innerHTML。渲染节流减少每个 Token 都触发全页更新；任务状态和引用仍应在权威事件到达时即时更新。

前端至少做六个可复现 Case：重复 seq 不重复文字；跳号后拉快照；提交超时后同键找回任务；SSE 断线但任务继续；取消后按钮状态正确；权限撤销后旧内容不可见。给每个 Case 保存输入事件、最终 UI 状态和网络调用次数。

五、今日面试题（检索日期：2026-11-21）

以下题面来自牛客用户自述，企业归属及面试经历未获官方核验。参考答案与追问为本文工程归纳。

1. AI 全栈项目的前后端交互和权限控制如何实现？绕过前端怎么办？

  • 方向 / 难度：前后端契约、权限 / 中高。
  • 参考答案：前端负责输入与状态展示；后端从认证会话确定用户和租户，对任务、会话、事件三类读取及写入逐一授权。前端隐藏按钮只是体验措施，不能作为访问控制。会话 Cookie 设 HttpOnly、Secure、SameSite，并按部署形态处理 CSRF；敏感身份不放在 URL。
  • 追问：用户打开任务页期间被移出租户，已有 SSE 连接如何处理？服务端重新校验或主动断开，前端收到拒绝后清除敏感缓存。
  • 来源：牛客“字节 AI 全栈开发实习一面”用户自述，正文“项目深挖”和 Web 部分；页面显示 07-27。

2. React 多组件共享任务状态时，怎样避免状态不一致？

  • 方向 / 难度：React 状态管理 / 中等。
  • 参考答案：让任务卡片或共享 store 持有单一的 TaskView，将任务 ID、状态与游标作为事实；加载标志、可取消按钮等从状态派生。SSE 事件统一经 reducer 应用，按序号去重，组件销毁时关闭订阅。不同页面重新获取任务快照，不依赖旧组件内存。
  • 追问：两个组件同时收到同一 model_delta 时，如何保证文本只追加一次？将去重放在共享状态层。
  • 来源：牛客“小厂全栈面经”用户自述，正文第 2–4 题涉及 React 组件与共享状态；作者写明 2026-08-26 面试。非大厂原题，用于补足前端基础。

3. 用户在接收 SSE 时刷新页面，后端任务会怎样？前端如何恢复？

  • 方向 / 难度：AI 全栈流式交互 / 难。
  • 参考答案：刷新只中断连接，后端按任务状态继续。新页面先读任务快照，再从 last_seq 续订；重连重复事件去重，缺口回快照。最终成功或失败以任务状态为准，不以连接 onerror 判断。
  • 追问：刷新恰好发生在“任务已创建、POST 响应未收到”之间，前端如何找回？持久保存这次提交的请求键并以同键同体重发，让服务端返回原任务；不能生成新键盲目再提交。
  • 来源：牛客“水滴 AI 全栈一面”用户自述，正文列出刷新、断连、续传追问；页面显示 10-19。该帖列题较多，单场题量无法独立核实。
